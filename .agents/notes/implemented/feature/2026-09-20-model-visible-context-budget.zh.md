# Agent Note: 模型可见的上下文预算

Status: implemented

[English](2026-09-20-model-visible-context-budget.md) | 中文

## 问题

meter 度量会话的上下文压力，但该度量的每个使用方都面向人。`dsh-token-meter` 为客户端载体注册 `tokenUsage`、`contextPressure` 与 `contextBreakdown`，它唯一的 host 使用方是压缩后端。因此，正在规划下一步的模型看不到自己还剩多少空间：它分不清再读一个文件是否仍放得下，并且只有在读到宣告结果的 checkpoint 前言时才得知历史已被替换。

这一缺口在压缩处最尖锐。压力检查在窗口的某个配置占比处触发，而摘要器被要求不得提及上下文曾被压缩，于是模型从一段被缩短的历史继续，却没有任何持久记录说明丢掉了什么、还剩多少余量。后果不是记账错误，而是规划错误：模型在没有证据的情况下，于"读取文件"与"委派他人"之间做选择。

本 note 延伸[可重放的 token meter 服务](../../archived/architecture/2026-07-15-replay-token-meter-service.md)与[预估 token 用量与请求上下文](../architecture/2026-07-29-projected-token-usage-and-request-context.zh.md)两项决策，它们拥有该度量及其 `projectedTokens` 字段。它不反转 meter 自身关于"占用率是参考数字而非计费记录"的决策：harness 仍然不据此做任何决定，本插件只是把这个参考数字呈现给唯一用它做规划的角色。

## 决策

### 预算读数是被追加的上下文，而不是工具

`@deepseek-ai/dsh-token-context` 注册一个前置的 `agent/pre-step` 监听器，在每个合格步骤追加一条带来源的 `UserMessage`，在追加调度与来源归属上跟随 [time-context](../../archived/feature/2026-07-14-time-context-plugin.md)。工具方案被否决：模型剩余的空间是每一步都在变化的连续状态，用工具意味着每个问题一次往返，而且只在模型已经怀疑自己需要发问时才报告。追加的读数与它所描述的步骤一同到达。

读数只携带投影确实持有的事实。占用行给出 `projectedTokens`，并在路由声明了容量时补上容量与百分比；总计行累加互不重叠的提供方桶；压缩行仅在部署声明了占比、且路由声明了容量时出现。尚无提供方用量的步骤不追加任何内容，而不是追加一条满是占位符的读数。

### meter 是硬依赖

本插件在 `inject` 列表中声明 `tokenMeter`。该服务自身的 `apply` 注册本插件所读取的三个投影单元，因此注入它正是这些单元存在的原因；没有 meter 的组合没有任何可报告的内容，必须不能挂载本插件却静默地不添加上下文。监听器仍然会对缺失的单元大声报错，因为激活之后消失的单元意味着组合已损坏，而不是该步骤无话可说。

### 压缩阈值由部署声明

`compactionThresholdRatio` 是配置，不是被发现的取值。本插件无法读取另一个插件的压缩策略，而 `dsh-compaction-basic` 默认为 `0.8`，同时允许 profile 按路由覆盖。在此照搬该默认值，会让配置被改过的部署收到针对一个它并不使用的点的余量报告，因此该字段默认未设置，省略它只会去掉压缩行。

## 考虑过的替代方案

**让 meter 提供读数。** 否决：`dsh-token-meter` 是无会话级调度的度量服务，其自身约定是它不添加任何提示词、消息、schema、工具或模型调用。由使用方拥有追加策略，meter 才能保持可重放且无使用方。

**改读 `measure()` 而非投影单元。** 否决：`measure()` 返回的是请求与响应的压力，而模型要问的是**下一次**请求将花费多少。`projectedTokens` 正是 meter 对这个问题给出的、已锚定的答案；从内部状态重算它只会复制 meter 的定价，而不是读取它。

**在数值变化时注入，而不是每个步骤。** 否决：模型是在选择步骤时读取预算的，因此一条因数值变化不大而被抑制的读数，恰好在它重要的时候是过期的。希望减少读数的部署设置 `refreshIntervalMs`。

**让 meter 可选并在缺失时静默跳过。** 否决：一个唯一输出就是该读数的插件，会因此与正常工作的插件无法区分，却什么也没添加。

## 后果

每条读数为请求增加约 40–60 个 token，并留在历史中直到压缩遮蔽它，这是本插件为换取模型的规划能力而引入的额外成本。把它挂在长会话 profile 上的部署应当预期这一取舍，并可用 `refreshIntervalMs` 调度读数。

读数低估了它自己所在的请求：它在 pre-step 期间追加，因此 `projectedTokens` 定价的是不含本条读数自身重量的请求。这些数字在最后一次提供方采样之后的部分还继承 meter 的固定估算器，因此 CJK 文本与 JSON schema 会被低估。

没有任何机制强制模型使用该读数。它让一个此前不可得的数字变得可得，而这是否改变 agent 的选择，是组合无法替它回答的行为问题。
